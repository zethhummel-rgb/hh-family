# HH — private family pilot

A separate application derived from Hummel Home's code. The original GitHub repository, website, Supabase project, accounts, calendar connection and notification service are not modified. This copy contains no family accounts, events, lists, OAuth secrets, refresh tokens, or notification subscriptions.

## Automatic invitation emails

In **HH Family → Edge Functions → Secrets**, add `HH_EMAIL_APP_PASSWORD` using the dedicated sender account’s 16-character Google app password. Paste it only into the secret field, never chat, source, or frontend environment variables. The password saved for Supabase Auth SMTP is separate from Edge Function secrets. `HH_EMAIL_FROM` optionally selects a different dedicated Gmail sender; its app password must belong to that account. Existing Auth SMTP settings do not change.

The `invitation-email` function sends over Gmail SMTP with TLS on port 465. It validates the signed-in user, then resolves the owner/host permission, recipient and expiry from the existing invitation. It cannot send to an arbitrary address supplied by the browser. The private delivery ledger prevents concurrent/repeated sends and limits attempts per sender, recipient and service. Retries reuse the same invitation; no email is sent just by deploying or listing pending invitations.

The invitation is a normal household/pilot invitation, not an automatic account creation or passwordless login. The recipient signs up or signs in with the invited address, confirms it, then accepts the invitation. Successful delivery status means Gmail accepted the email; inbox or Spam placement must still be checked. If delivery cannot be confirmed, the UI preserves the copyable link and offers retry after a minute. Links are shown only when created; tokens are stored hashed, so a lost link requires a new invitation. The email audit tables record recipient, attempt times and status, not message bodies or SMTP credentials.

For an existing installation, apply only the additive invitation-email migration once. Never reapply the initial bootstrap. Then deploy `invitation-email` with its `index.ts`, `message.ts` and `smtp.ts`, leaving `verify_jwt=false` because the function explicitly validates the bearer session through `auth.getUser`.

## Families

Each household names its own home. Its owner can rename the home, add child/non-login profiles with colours, and later link those profiles to existing family accounts while preserving event tags. Accounts choose their own colours and personal palette. There are no preloaded relatives, events or lists. For the first pilot, times and reminders use Eastern time (America/Toronto); cross-timezone support is not implemented.

HH calendars work without Google, including daily/weekly/monthly/yearly repeats, custom intervals, count/date endings, occurrence edits/deletions and push reminders. Apply `database/native-calendar-repeats.sql` after the existing calendar/member-colour/push migrations. Native series store one household-scoped master with validated exceptions and optimistic version checks. The same Eastern-time expansion runs in calendar views, search and push delivery. Monthly dates absent in a month and February 29 in non-leap years are skipped. Native search shows one representative occurrence per series plus matching edited dates. Google remains optional; explicitly connecting copies native series and their changed/cancelled occurrences with retry-safe IDs.

Pilot invitations expire after 14 days, are single-use, require the exact confirmed email and reserve one of fourteen household places. Pending unused links can be revoked. Only a server-authorized host can issue them. A registered user without membership or an eligible invitation cannot create a home or see family data. Family member invitations expire after seven days and cannot create a separate home.

Profiles without a login route reminders to the household's opted-in accounts. Linked profiles route to the linked account. People and provider connections are always looked up inside the requesting household. Profile links cannot point at an account in another home. Notifications require device opt-in; iOS requires installing the PWA first.

## Staying signed in

Sign-in and signup offer **Stay signed in on this device**, checked by default to preserve existing HH logins. Checked sessions use HH's existing `home-together-auth` local-storage entry and survive closing/reopening the browser or installed app when that browser keeps its data. Unchecked sessions use session storage with a separate key/channel for the current tab's browsing session; they survive a reload and are not copied to an unrelated tab. Browser session restore may retain session storage. Passwords are never saved by this option.

Both choices keep Supabase's normal token renewal and server-side session rules. HH rechecks the saved session on focus, reconnect and page restoration. A storage failure keeps the current visit usable and shows that the login could not be saved. Explicit Sign out ends the current session/device (`scope: local`), so it does not sign out other devices. Password changes, account deletion, revoked sessions, cleared browser data and separate Safari/installed-app storage can still require signing in again. The isolated password-reset client remains memory-only. No backend session limits are relaxed.

## Household reminder job isolation

The existing minute cron job now queues one authenticated pg_net request per household with current opted-in members. Each request handles only that household, with an independent 90-second lease, a 20-second delivery deadline and bounded recurrence expansion. Native masters are processed in pages of 25. Current membership, per-device claims, retries and expired-subscription cleanup remain in force. A heavy or failed calendar cannot hold a global household-processing loop.

Inspect `private.push_household_runs.last_run_at/last_result` for individual household jobs. `limited: true` means the recurrence or processing budget was exceeded and needs investigation. `private.push_settings.last_result` reflects the latest household result rather than a full multi-household sweep. Expired delivery records are still removed after 30 days. A terminated job’s lease expires so the next minute runs can recover within the existing bounded catch-up window.

## One-time import from an existing Google calendar

Settings → Calendar → Import a Google calendar lets a current household member grant separate read-only consent, pick a source calendar and review/select supported events or series. Skip tagging for this entire import is the default; members can instead assign people or Everyone once for all selected events. New events retain their normal family-tagging defaults. Skip tagging creates a calendar-only event with no person dots and no notifications, visible in the unfiltered household calendar. It remains unassigned when edited; people and reminders can be added later. Person tags affect filtering and reminders, not visibility: all household members can see the imported content. The confirmation explains this before saving. The default 30-minute reminder can be disabled for the import.

Imports save native HH records atomically. They do not alter the source Google calendar, copy attendees or send guest invitations, establish ongoing incoming synchronization, or change native calendar authority. An enabled outbound Google copy receives the new HH records through the normal outbox. The server excludes that household's existing outbound copy calendar from source choices to avoid importing HH's own copies back into HH.

The import uses the existing registered `/functions/v1/google-calendar/callback` URL with separate single-use PKCE state. Import tokens and previews are bound to the initiating HH account and household; membership is rechecked on every action. After Google returns, a single-use completion token in the URL fragment must be exchanged through that same signed-in HH account before any calendar list or event access is available. The frontend removes the fragment immediately; it is never sent in a referrer or stored persistently. Import access tokens are encrypted temporarily in Vault, with no stored import refresh token. Completion, cancellation, expiry and account/household removal clean up temporary credentials. A household-scoped source identity ledger prevents repeats, concurrent duplicates and resurrection after deletion. Importing never overwrites a previously imported event with newer Google changes.

## Event countdowns

In the event editor, **Make a countdown** adds a shared, thin row directly below the Home motivational sentence and above household updates. Each enabled event/series gets one row, ordered by its next start. Rows show calendar days in America/Toronto (including Today!/Tomorrow), open freshly loaded event details, and disappear after the start day or when switched off/deleted. A repeating countdown follows its next valid occurrence, including moved/cancelled dates, skipped short months and leap years. Change that setting through **The whole series**; one-occurrence edits preserve it. Calendar filters do not hide the household’s countdowns.

The additive `event_countdowns` migration adds `household_events.countdown_enabled`, false by default, with only that column’s update grant. Existing household/source RLS, optimistic versions, notification choices and event fields are retained. Countdown choices are stored with their event, so saving is atomic, old clients preserve the field on unrelated edits, and deletion needs no separate cleanup. Countdowns use the same native-master snapshot as the calendar, so far-future plans work beyond the visible month/60-day Home range without another integration or duplicate data request. Google’s optional copy remains independent. An existing Google-source household can use countdowns after its preserved transfer into HH finishes.

Apply this migration to HH Family `njpdqiwrwgoothkstoql` before publishing the frontend. Fresh-project assembly includes it; do not bootstrap an existing project. The recurrence engine’s opt-in starts-only search is used by Home countdowns; existing view/search/reminder callers keep overlap semantics. No Edge Function deployment is required. Tests cover dates/DST, far-future and recurring targets, source/member isolation, shared edits, untouched older fields and snapshots.


## Grocery details

Groceries support Deli, optional quantity/unit and store fields, and editing from Home or the full list. Quantity +/− controls change by one; decimal quantities can be typed. A per-account/household device preference switches grouping between Department and Store. Store grouping combines matching store names regardless of case, keeps unassigned items under No store set, and shows each item’s department. Store filtering and search work with either grouping. Picked-up items retain their details and can be edited and added back for the next shop. Saved staples and meal ingredient categories also include Deli; adding them to groceries retains their existing duplicate handling and title text (including amounts already written in titles).

Apply the additive `grocery_details` migration to HH Family `njpdqiwrwgoothkstoql` before publishing. It preserves old fields, adds nullable grocery-only metadata, broadens the two category checks and meal ingredient validator, and uses the existing `reminder_version` as the grocery revision. A grocery-only trigger advances that revision for old clients too, while task recurrence remains owned by its current trigger. Stale edits/pickups/deletes fail without overwriting another member’s changes. Existing RLS and transition/cutover guards remain. Legacy active transfers keep their existing list behavior; the new details editor waits until transfer completion. Fresh provisioning includes this SQL; never bootstrap an existing database. No Edge Function deployment is required.

## Returning to the shopping list

HH remembers the last full screen per account and household on the same browser/device. Groceries also retains its search, selected store and scroll position; the existing department/store grouping preference remains separate. Only validated navigation preferences are stored under `hh:navigation:v1:<user>:<household>`, never household records, auth credentials, editor drafts or open dialogs. Storage failures fall back to the current in-memory visit. Notification destinations take priority; activity and meal-to-grocery links retain their explicit destinations. Scroll restoration waits for the list to load and pauses for onboarding/dialogs, and user scrolling or changing filters cancels a pending restoration.

Repeated Supabase SIGNED_IN events for the same verified auth client/user recheck current membership without unmounting Household. Missing/changed membership, recovery, signout, account changes and verification failures retain access checks; stale responses cannot restore an old identity. Grocery data refreshes on focus, page show, return to a visible page, reconnect and the existing interval. This is continuity across app wake/reload, not an offline write queue or a guarantee of device login persistence when Stay signed in is off. Tests cover real component auth transitions, local navigation state and synthetic Chromium/WebKit reopen flows.

Store grouping in Groceries displays department subsections inside each store, including No store set. The full grocery list and picked-up rows show a fixed narrow Qty column between the checkbox and item title, with optional units underneath. Missing quantities display a dash; amounts written in historical item titles are not parsed or changed. Home retains its compact item details.

Meal ingredient quantities use the same optional quantity/unit controls as grocery editing. `meal-ingredient-quantities.sql` extends the strict JSON validator with optional numeric quantity (0 < q <= 9999, at most three decimals) and trimmed unit (up to30 characters, quantity required). Old ingredient objects/text are preserved without conversion. The invoker shopping RPC writes structured amounts to groceries and matches normalized name, quantity and normalized unit; different amounts remain separate. Existing membership, versions, transaction/transfer checks and limits remain. Deploy this additive migration before the ingredient editor frontend; never bootstrap an existing project. The mobile body-level navigation now tracks visual-viewport changes with a fixed bottom offset and avoids a transformed navigation layer. Physical iPhone dynamic-toolbar/keyboard behavior still needs a device check.
